aerpawlib

2025 - Present · AERPAW

The official vehicle control library for AERPAW, NC State's research testbed for advanced wireless communications and autonomous aircraft.
Built

I maintain the official AERPAW/aerpawlib repository, which provides the Python programming interface that visiting researchers use to fly autonomous drones and drive ground rovers during experiments. I transitioned the project from its original DroneKit foundation over to MAVSDK, preserved backward compatibility for existing scripts, and added a modern asynchronous API for newer experiments.

Hard parts
  • The testbed safety filter strictly restricts vehicle commands to takeoff, landing, waypoints, and yaw, requiring all takeoff altitudes to stay between 20 and 100 meters and landings to finish within 5 meters of home.
  • Direct flight mode changes are blocked by the safety layer, so guided mode has to be maintained using explicit command messages without dropping communication links.
  • Safety validation logic has to coordinate directly with the companion virtual machine rather than running locally or through operator consoles.
  • Velocity commands and geodesic navigation calculations needed updates to handle latitude scaling properly and prevent newer movement requests from being prematurely cancelled.
  • Coordinating multiple vehicles over ZeroMQ required switching to an acknowledged messaging handshake so state transitions would not be dropped under load.
Learned
  • Working within a hardware testbed means the physical safety filter dictates software requirements just as much as the autopilot library itself.
  • Software-in-the-loop simulations are essential for catching basic logic errors, but real flight testing is still needed to uncover edge cases in testbed infrastructure.
  • Providing a backward-compatible wrapper alongside a redesigned API made it possible to modernize the library without breaking existing researcher experiments.

PyAerial

2024 - Present · AERPAW

An airspace awareness and aircraft tracking system that ingests Mode S and ADS-B signals, evaluates geofence boundaries, and displays live flights on a radar map.
Built

I built PyAerial as a complete rewrite of my earlier aircraft tracking project, airstrik.py. The application decodes raw ADS-B radio signals using pyModeS, evaluates custom Shapely geofence boundaries, and separates the real-time tracking daemon from the web dashboard so that user interface traffic never interrupts signal decoding.

Hard parts
  • Decoding Compact Position Reporting coordinates requires a reliable reference position separate from boundary areas to prevent receiver errors from producing false aircraft locations.
  • Merging signals from multiple ground receivers requires comparing signal strength and Hamming distance while correctly wrapping compass heading boundaries across zero degrees.
  • Estimated arrival calculations had to account for both straight paths and turning maneuvers to ensure aircraft approaching boundaries are detected consistently.
  • Geofence notifications needed timing hysteresis to avoid sending multiple alerts when an aircraft briefly skirts the edge of an airspace boundary.
  • The background tracker maintains a persistent heartbeat in Redis so that read-only web workers cannot accidentally overwrite live tracking state.
Learned
  • Handling radio broadcast formats requires validating packet integrity and message order before attempting to plot coordinates on a map.
  • Separating real-time state in Redis from long-term flight logs in SQLite provides much better performance and reliability than trying to use a single database for both.
  • Geofence rules work best when they include explicit flight parameters like altitude ceilings, ground speed, and arrival time rather than just simple point checks.

DroneTracker

2024 - Present · AERPAW

An automated tracking service that points AXIS pan-tilt-zoom cameras at flying drones using live GPS coordinates from Kafka and records flight video over VAPIX.
Built

I developed DroneTracker as a containerized service that reads real-time drone position and velocity telemetry from Apache Kafka, computes the required camera orientation angles, and issues pan, tilt, and zoom commands to AXIS optical cameras over the VAPIX network protocol. Because existing control libraries only supported movement commands without video recording, I also forked and updated the camera client library to manage recording sessions on the camera's local storage.

Hard parts
  • Translating geodetic coordinates into camera angles requires calculating spherical bearings for pan, elevation angles for tilt, and optical zoom steps based on distance and vehicle dimensions.
  • Handling camera compass offsets requires wrapping angles correctly into the camera's native pan range of minus 180 to positive 180 degrees.
  • Supporting predictive lead times requires managing coordinate frame conventions carefully so vertical velocity directions match physical drone movement.
  • Network delays and stale telemetry packets had to be filtered out so the camera would hold a resting position rather than slewing toward outdated coordinates.
Learned

Connecting physical cameras to network telemetry requires handling camera hardware mechanics, network authentication, and video storage management alongside the mathematical coordinate transformations.

ML-Ticker

2026 · Merrill Lynch

A command line financial data tool built during my internship at Merrill Lynch, featuring FactSet FQL querying, a safe formula evaluation engine, and Excel reporting.
Built

I built ML-Ticker as an internal Python command line application for equity research workflows, allowing analysts to retrieve FactSet market data, define custom financial metrics through configuration files, and export formatted reports to terminal tables and styled Excel workbooks.

Hard parts
  • Allowing analysts to write custom formulas required building a restricted syntax tree evaluator that safely prevented arbitrary code execution while supporting mathematical expressions.
  • Formulas frequently depended on other calculated metrics, requiring an internal dependency graph to resolve evaluation order and detect circular references before querying external APIs.
  • Financial queries often returned incomplete data points that needed typed missing-value representations to keep calculated workbook columns from failing silently.
  • Managing differences between point-in-time portfolio holdings and historical time-series queries required separate data models and multi-stage retrieval pipelines.
Learned

Building internal research tools requires validating user configurations and mathematical expressions up front so errors are caught before making expensive data queries.

Strife

2026 - Present · Discord Bots

A multiplayer game platform for Discord that runs turn-based matches inside message threads, featuring plugin game engines, PostgreSQL persistence, and crash recovery.
Built

I developed Strife as a complete rewrite of my earlier Discord bot PlayCord, creating an extensible platform where multiplayer turn-based games run in dedicated message threads. The architecture uses a modular plugin system so that the exact same game logic runs interactively on Discord, replays historical matches, and runs in local command line sessions.

Hard parts
  • Recovering ongoing matches after bot restarts required saving every player action to an append-only database log and replaying moves sequentially to restore game state.
  • Handling user interface interactions across Discord threads required encoding signed message identifiers and managing automated timeouts for inactive lobbies.
  • Preventing unresponsive game code from blocking Discord's asynchronous event loop required isolating player turns inside bounded background execution pools.
  • Designing relational database migrations to track active match states and foreign key relationships across players, guilds, and historical move logs.
Learned

Building a reliable online gaming bot requires treating state persistence as the central priority, using deterministic game rules and an append-only move log so that crashes never corrupt active games.

NCSU Parking

2026 · Solo Projects

A predictive parking availability model for NC State campus decks that combines historical occupancy feeds with campus event schedules and validates machine learning models against strong seasonal baselines.

Notes

I built a data collection and forecasting pipeline for NC State campus parking decks. A background collector polls public occupancy APIs and university event calendars into PostgreSQL, engineering features such as five-minute time grids, lag statistics, rolling occupancy averages, geographic event distances, and academic calendar dates. The forecasting pipeline evaluates an hour-of-week seasonal baseline and only retains per-lot XGBoost models when they achieve lower validation error than the simple median across forecasting windows ranging from fifteen minutes to twenty-four hours. Model training runs as a decoupled batch job, keeping the lightweight Streamlit dashboard responsive.
